Act 1 · 2004 · The Beginning

People say "Happiness is hearing something you weren't supposed to". So in order to find happiness, we go and gossip about others' lives. Baby Hope was 4 years old and thought why don't I build a place where people can gossip together? That's when Gossip.com was born. It's basically an MVC PHP web application, with PHP templates for CRUD actions in combination with HTTP forms, with MySQL underneath, and everything running on a rented VPS for $5/month. Well, at that time, things were just that simple. It worked really well for a couple of years — people shared and gossiped about their neighborhoods, which made the whole town very active and fun.

Act 2 · 2007 · The Crash

Couple of years go by, things are going well. Traffic is slowly growing. Gossip is flowing. No problem. Until one night in 2007, something happened. Something big. I don't know what it was — a celebrity scandal? A neighborhood drama? A very spicy piece of gossip about someone's wife? Whatever it was, overnight, everyone in town opened Gossip.com at the same time.

And the server... did not survive. At 2:47am, CPU hit 100%. The database ran out of connections — all 500 of them. And then nginx just gave up. By 2:47:10, server unreachable. That terminal log you're looking at right now — that's the kind of thing that wakes you up at 3am in a cold sweat. Baby Hope learned what a production incident is.

Now the first instinct here — and I think most of us would have the same instinct — is just make it bigger. More RAM, more CPU, bigger machine. That's vertical scaling. So Hope upgraded. $5 a month to $40. Traffic grew more. $40 to $320. More traffic. $320 to $640 a month. And then... nothing. Ceiling. There is only so big a single machine can get. The hardware just stops scaling.

So vertical scaling buys you time. That's it. It's not a solution, it's a delay. And that's okay to know — next time someone says "just scale up the server", you know exactly where that road ends.

Beat 2.2 · Horizontal Scaling + Sessions

So when you can't go up anymore, you go out. Instead of one big machine, you spin up multiple smaller ones and split the traffic between them. That's horizontal scaling. But now you have a new problem — who decides which server handles which request? You need something sitting in front of all of them to receive every incoming request and decide where it goes. That's a Load Balancer.

The simplest strategy is round-robin: request 1 goes to Server 1, request 2 goes to Server 2, request 3 back to Server 1. Just taking turns. Simple, easy to understand, works well enough most of the time.

But there's a problem with that. Requests are not equal. Some requests are fast — just fetching a username, done in 5 milliseconds. Some requests are heavy — generating a full news feed, joining 10 tables, running for 2 seconds. Round-robin doesn't know that. It just rotates. So randomly, all the heavy requests could pile onto Server 1, while Server 2 is breezing through light ones. Server 1 is drowning, Server 2 is bored. That's imbalanced and inefficient.

So a smarter approach is to let the load balancer actually look at the servers before deciding. It checks things like how many active connections each server has, or how fast each server has been responding lately. If Server 1 is already handling 20 slow requests and its response time has crept up, new traffic goes to Server 2 instead. It doesn't take turns blindly — it routes based on where the traffic will actually be handled faster.

So Hope sets this up. Two servers, load balancer in front. Looks great on the diagram. Ships it. And then the support tickets come in. "I keep getting logged out." "Every time I refresh I have to log in again." Hope checks the code — nothing wrong. Checks the servers — nothing wrong. Logs in himself, refreshes a couple of times — and suddenly, he's logged out too.

Here's what was happening. When you log in to Gossip.com, the server creates a session — a small record in its memory that says "user ID 42, authenticated." That record lives inside the memory of that specific machine. So your first request hits Server 1. Server 1 creates the session, remembers you. Your next request — load balancer round-robins it to Server 2. Server 2 looks in its memory. Nothing. You're a complete stranger to Server 2. Back to the login page. This is not a bug. This is architecture. A very embarrassing architecture, but still architecture.

Now someone might say — well, what if we use IP hash? Always send the same user to the same server. Problem solved, right? Kind of. That's called sticky sessions. It works — until Server 1 goes down. The moment it crashes, every user who was "stuck" to it loses their session. And it creates uneven load, because some users are way more active than others. You're not solving the problem. You're just hiding it.

So we have to ask a deeper question: why does this break at all? It breaks because our application is stateful. It's holding information — the session — between requests, inside its own memory. That's state. And that state only exists on one machine.

So can we make it stateless? And what does stateless actually mean?

Stateless means: after the server handles your request and sends back a response, it forgets everything about you. No memory. No record. The next request could go to a completely different server and it wouldn't matter — because there's nothing to carry over.

But if the server doesn't remember who you are... how does any server know you're logged in?

The answer is: we move the state out of the application layer entirely. Instead of the server holding your session in its own memory, we store it somewhere that every server can reach — the database. When you log in, a session record gets written to the database. When any request comes in, the server looks up that record from the database. Server 1 and Server 2 both query the same place. They both see the same data. The database becomes the single source of truth.

Now your servers are interchangeable. Server 1 can go down, Server 3 can come up, and nothing breaks. No user notices. Because every server is just reading from the same database anyway. You can run 50 servers and they all agree on who is logged in — because they all ask the same question to the same place.

That's stateless. Move the state out. Let the database remember. The servers just process.

Act 3 · 2009 · Performance

A couple of years go by. The servers are stable. The load balancer is doing its job. But Gossip.com is growing fast — more users, more gossip, more traffic. And a new problem starts quietly building up. The database is getting slow.

Hope pulls up the database logs. And there's something immediately obvious. The same five queries are running over and over again. The homepage feed. The trending topics. The most gossiped-about neighbors. These queries run forty times per second. The same query. Returning the same result. Hitting the database every single time.

And these are not simple queries. The feed query joins multiple tables, sorts by time, filters by who you follow. It's expensive. Run it once, maybe 800 milliseconds. Run it forty times a second across all your servers — the database starts to sweat. Response times creep up. Users notice the site getting sluggish.

Beat 3.1 · Caching + Redis

So here's the question: does the homepage feed actually change every millisecond? Does the trending list update forty times per second? No. A user posts something new every few minutes at best. The trending topics barely shift. Yet we're hitting the database forty times a second asking for the exact same answer.

What if we just... remembered the answer? Instead of asking the database every time, we ask it once, keep the result somewhere fast, and reuse it until the data actually changes. That's caching. Compute once, serve many times.

The first instinct might be to store it in the server's own memory. Just a local variable. Fast, easy. And it works — until you remember you have ten servers. Each server has its own memory. Server 1 caches the feed. Server 2 doesn't know about that. Server 2 runs the query again. Server 3 runs it again. Each server ends up with its own copy, and those copies might not even agree with each other. That's worse than no cache.

So the cache needs to be shared. One place that all servers read from and write to. When Server 1 fetches the feed and stores it there, Server 2 and Server 3 find it already — no database call needed. That shared in-memory store is what Redis is. Reads happen in under a millisecond because everything lives in memory, not on disk. Any server checks Redis first. Cache hit — return immediately. Cache miss — go to the database, get the result, store it in Redis for next time.

But now there's a new question. What happens when someone posts something new? The cached feed is now stale. How long do you keep a cached result before it's too wrong to use?

One approach is TTL — time to live. You say: this cache entry is valid for 60 seconds. After that, it expires automatically, and the next request fetches fresh data from the database. Simple, predictable. The tradeoff is that users might see data that's up to 60 seconds old. For a gossip feed, that's probably fine.

The other approach is cache invalidation — when the data changes, you immediately delete the cached version. Someone posts something new, you delete the "homepage-feed" entry. The very next request finds nothing in cache, goes to the database, gets fresh data, stores it again. More accurate, but more work — every place in your code that writes data needs to know which cache entries to clean up.

There's a famous quote in computer science: "There are only two hard problems — naming things, and cache invalidation." For naming things, I think we all know how that goes. And for cache invalidation — once you go deeper, you'll start dealing with mutexes, locks, probabilistic early expiry, just to make sure your cache stays correct and doesn't accidentally blow up your database the moment it expires. It gets complicated fast. Which is why most teams start with TTL, and only reach for the harder stuff when they actually need to.

Beat 3.2 · DB Indexes

So Redis is helping a lot. The database is no longer getting hit forty times a second for the same feed query. But cache misses still happen. New queries get added as features grow. And some of them are just... slow. Not because they run too often, but because they're slow on their own, even the first time.

Hope runs a command to inspect one of the slow queries — basically asks the database to explain how it's processing it. And the database says: full table scan. 10 million rows scanned. Found 847 matching rows.

Full table scan means the database reads every single row in the table, one by one, top to bottom, checking whether each one matches your condition. Think of it like finding someone's name in a phone book — but there's no alphabetical order, no sections. You start from page 1 and read every single entry until you reach the end. With 10 million rows, that's a lot of reading. Even if you only want a few results.

So the question is: can we give the database a shortcut? Instead of reading everything, can it somehow jump straight to the rows it needs?

Yes. That's what a database index is. Think of the index at the back of a textbook. You don't read every page to find where "load balancer" is mentioned. You go to the index, find the entry, it tells you exactly which pages. You jump straight there. A database index works the same way — it's a separate, sorted data structure that maps a column's values to the exact locations of the matching rows. When the database searches for all posts by user ID 42, instead of scanning 10 million rows, it looks up user ID 42 in the index and jumps straight to those rows. Query time drops from seconds to milliseconds.

So you add an index on the columns you search by most — user ID, post date, whatever your queries filter on. Immediate improvement.

But there's a tradeoff. Every index speeds up reads but slows down writes, because every insert has to update the index too. And indexes take space. So you don't index blindly — you look at which queries are actually slow and add indexes there.

Together, caching and indexes are the two most effective tools for database performance. Caching reduces how often you ask the database. Indexes make each ask faster when you do.

Beat 3.3 · CDN

Here's something about gossip that Hope didn't fully anticipate: gossip is not local. Gossip is a fundamental human need. People everywhere, in every country, in every timezone — they all want to talk about other people's business. Gossip.com started in one small town, but the internet doesn't have borders. Word spread. Users from Japan found it. Users from Germany found it. Brazil, Australia, the US. Turns out everyone, everywhere, has something to say about their neighbors. Gossip.com went global.

And that's exciting — until the complaints start coming in. Not from local users. From the new ones. "The site is slow." "Images take forever to load." "I clicked a profile photo and waited five seconds." Hope checks the servers — healthy. Checks the database — fine. Everything looks good on paper. But users in Tokyo, in Germany, in Brazil are getting terrible load times.

Here's the thing about the internet that's easy to forget: data travels through physical cables. And physical cables have physical distance. A user in Tokyo requesting a photo stored on a server in Singapore — that request travels thousands of kilometers, the server responds, and the response travels thousands of kilometers back. Even at the speed of light, that adds up. That delay is called latency. And no amount of code optimization fixes it. You can't refactor your way out of geography.

So Hope looks at what's actually being served. HTML, API responses, the dynamic stuff — yes, those need the server. But images, profile photos, CSS files, JavaScript files — those are just static files. They don't change per user. They don't need business logic. They're the same file for everyone who requests them.

So the question is: why are we routing them through our application server at all? What if, instead of every user in the world reaching back to one server in Singapore, we stored copies of those files in servers physically close to the users? A server in Tokyo, one in Frankfurt, one in São Paulo. When a user in Tokyo asks for a photo, they get it from the Tokyo server — milliseconds away, not thousands of kilometers.

That's a CDN — Content Delivery Network. A global network of servers called edge nodes, spread across the world, caching your static content close to your users. The first time someone requests a file from a region, the edge node fetches it from your origin server and keeps a copy. Every request after that is served from the edge. Fast, regardless of where in the world the user is sitting.

And your application servers are now free from doing work they were never supposed to do. They only handle requests that actually need logic — API calls, database queries, user-specific responses. Not serving the same image file ten thousand times a day.

The rule is the same as caching, just at a different layer: if the content is the same for everyone and doesn't change often, it doesn't need to go through your server. Push it to the edge, as close to the user as possible.

Act 4 · 2011 · Async

By 2011, Gossip.com is a real platform. Global users, solid infrastructure, database performing well. Hope decides to add new features — notifications, email digests, personalized feeds. Product is happy. Users will love it. He ships it.

And then someone posts something. And just... waits. The page spins. Five seconds. Seven seconds. Nine point two seconds. Then finally — the post appears. Nine seconds to publish one piece of gossip. On a gossip site. Where the entire point is that information spreads fast.

Beat 4.1 · The Blocking Chain

Hope looks at the code. The post endpoint does this: save post to database — 200 milliseconds, done. Then notify all followers — 3,200 milliseconds. Then send email digests — 2,400 milliseconds. Then update everyone's personalized feed — 3,100 milliseconds. Total: around nine seconds. The user sits there watching a spinner while their server is off sending emails to strangers.

Now here's the question — and it seems obvious once you ask it: does the user need to wait for the notification email to be sent before they can see their post published? Does the post only exist after every follower has been notified? No. The post is saved. That's done in 200 milliseconds. Everything else is a side effect. The user doesn't need to be involved in any of it.

The problem is that all of these steps are synchronous. One thing happens, then the next thing waits for it to finish, then the next thing waits for that. Like a line at a counter where everyone queues up even though they could all be helped at the same time. The user's request is stuck at the back of that line.

What we need is a way for the post service to say: "I'm done, post is saved" — and then walk away. Let the notifications, the emails, the feed updates all happen in the background, independently, without blocking the user's response.

Beat 4.2 · Job Queue

So the solution pattern is: instead of doing everything inline during the request, you write a job into a queue and return immediately. The user gets their response in 200 milliseconds. The rest happens in the background.

The simplest version of this — and what most teams actually start with — is a jobs table in the database. When the post is saved, the same database transaction also writes a record: "send notifications for post 991, status pending." A background worker runs continuously, polling that table for pending jobs, picking them up one by one, and processing them. The user is long gone. The notifications go out eventually. Nobody waited.

This works really well, and it has a nice property: because the job is written in the same database transaction as the post, you get atomicity for free. Either both the post and the job are saved, or neither is. You can't save the post and lose the job record. That guarantee matters.

One thing to be careful about: what if the worker picks up a job, starts processing, and crashes halfway through? The job gets retried — which means it might run more than once. So your logic needs to be safe to repeat. Don't send two emails because the worker crashed after the first one.

This DB-backed job queue approach is simple, reliable, and gets you surprisingly far. It's how most teams handle async for a long time. The limits only start showing up later — when the system grows larger, when you have many independent services all needing to react to the same events, and when the volume of jobs is too high for a single table to handle cleanly. But that's a problem for a future version of Gossip.com.

Beat 4.3 · WebSocket + Redis Pub/Sub

The job queue fixed the posting experience. User clicks post, 200 milliseconds, done. But now flip to the other side. You're a user sitting on Gossip.com waiting for fresh gossip. How do you find out that someone just posted something new? The page has to check. Every few seconds the browser sends a request: "anything new?" Server says no. Three seconds later: "anything new?" No. Three seconds later: "anything new?" Still no. This is polling. And it's exactly as wasteful as it sounds — thousands of users asking the same question every three seconds, most of the time getting told nothing happened.

And even when something does happen, there's a lag. A post goes up at second zero. Your browser asks at second three. You find out at second three. Not real-time. Close enough for email. Not good enough for a platform where the whole appeal is that gossip feels immediate and alive.

The issue is the HTTP model itself. HTTP is request-response: the client asks, the server answers. The server can never speak first. It just waits to be asked.

What if we flipped that? Instead of the client asking over and over, you open one persistent connection between the client and the server — and keep it open. Now the server can push data the moment something happens. No polling, no lag. Someone posts gossip, the server says "here it is" directly to every connected client. That's WebSocket. Full duplex, persistent connection, server push. The feed feels alive. Users see new posts appear without refreshing. That's what the product was always supposed to feel like.

But then Hope looks at the infrastructure. WebSocket connections are stateful. Each one is a long-lived, persistent line between a user and a specific server. User A is connected to Server 1. User B is connected to Server 2. User C posts something new — Server 1 processes it and needs to push the update to every connected user. But User B's connection lives on Server 2. Server 1 has no way to reach it directly.

Same problem as Act 2 with sessions. Different layer, exact same shape.

The solution follows the same logic: move the coordination out of the individual servers into a shared layer. When Server 1 needs to broadcast an event, it publishes to a shared channel. Every server subscribes to that channel. Server 2 receives the broadcast, looks at its own connected clients, finds User B, and pushes. Redis handles this — not as a cache this time, but as a pub/sub broker. One server publishes, all servers subscribe, each one delivers to whoever is connected to it. The WebSocket layer becomes stateless at the coordination level — which is the only way it works at scale.

Act 5 · 2014 · Microservices

By 2014, Gossip.com has a team. Real engineers. Multiple product squads working in parallel — one team on the feed, one on notifications, one on payments. And they all work in the same codebase. One giant application. User management, posts, comments, notifications, payments, feeds — all tangled together. Every feature touches every other feature. Every deploy deploys everything.

And one Friday afternoon, the notification team pushes a fix. Small change. A regex update for filtering spam. Goes through review, looks fine. Deploy. Within minutes, the payment flow is broken. Users can't check out. Support tickets flood in. The notification team's code somehow broke payments. Two hours to roll back, diagnose, fix. A Friday. It's always a Friday.

Beat 5.1 · Service Decomposition + Kafka

The problem isn't the engineers. The problem is that everything is coupled. When one part of the system changes, there's no way to be sure it won't affect something completely unrelated. The notification service and the payment service share the same process, the same memory, the same deploy pipeline. A bug in one is a bug in all.

So the question is: what if they didn't share any of that? What if each major piece of functionality ran as its own independent service — its own codebase, its own deployment, its own process? The notification service lives on its own. The payment service lives on its own. They don't know about each other's internals. A bug in notifications crashes notifications. Payments keeps running.

That's the idea behind microservices. Instead of one large application doing everything, you decompose it into smaller services, each responsible for one focused domain. Each service can be deployed independently — the payment team ships on Tuesday, the notification team ships on Thursday, nobody waits for anyone. Each service fails independently — a crash in notifications doesn't touch payments. And each service scales independently — the feed service might need 20 instances during peak hours while the payment service only needs 2. With a monolith, you'd have to scale the entire application together, which is wasteful. Now you scale exactly what needs scaling, nothing more.

So Hope splits everything up. Services deployed. Teams are happy. And almost immediately, the first real distributed system problem shows up. Each service now has its own database — that was intentional, sharing a database would just couple them at the data layer. But now: when the Post service creates a post, how does the Notification service know? It can't query the Post service's database directly. And calling the Post service's API synchronously blocks everything again — the same problem we had before.

So here's the deeper question underneath this. You have five services that can't share a database. They all need to know about a new post. Do they all have to know right now, at the exact same instant? Think about what that would require — you'd have to freeze everything, wait for every service to confirm it's updated, then proceed. And if one service is down? You either wait forever, or you say the post never happened. That's not a system, that's a deadlock.

So most systems make a different choice: keep running, keep responding, and accept that some services might be a few seconds behind. The data will be right — just not instantly everywhere. That's eventual consistency. And yes, there's a theorem that formally names this tradeoff — CAP — but you don't need to memorize it. You just lived the reasoning. The network will fail, that's physics, and when it does you're choosing between stopping the world or accepting a brief lag. Most systems choose the lag. And that choice shapes how everything communicates from here.

Instead of synchronous calls that block and demand immediate consistency, services communicate through events. Things that happened. The Post service says "post 991 was created" — drops that into a shared event channel and moves on. The Notification service, the Email service, the Feed service each receive that event and react in their own time, independently, without blocking anything. That's where Kafka comes in — a distributed, durable event log built exactly for this. Services publish events to it. Other services consume from it at their own pace. One event, many consumers, fully decoupled.

Beat 5.2a · API Gateway

Now you have ten services. And the client — the mobile app, the browser — needs to talk to them. Do they call each service directly? That means the client has to know the address of every service. Every time you add a service or move one, the client has to update. And every service needs to handle authentication on its own — figure out who's making the request, whether they're allowed.

The clean solution is a single entry point. One door that everything goes through. Behind that door, it routes to the right service. That's an API Gateway. The client only knows one address. The gateway handles the routing, rate limiting, and authentication — then passes the request through to whichever service needs to handle it.

Beat 5.2b · JWT

But there's still the question of identity. In a monolith, auth was simple — the session was in the database, every part of the app could check it. Now you have ten services. Do they all call the auth service on every single request? That's a lot of extra calls, and it makes every service dependent on auth being available.

A better approach: when the user logs in, the auth service issues a token — a small, self-contained piece of data that says "this is user 42, they have these permissions, signed by us." The token travels with every request. Any service can verify it on its own, without calling auth again. The signature ensures it hasn't been tampered with. That's a JWT — JSON Web Token. Identity becomes stateless and portable across the whole system.

Beat 5.2c · OAuth2 / OIDC / SSO

Around this time, product comes to Hope with two requests. First: users are dropping off at signup. Nobody wants to create another account, remember another password. "Can we just add Login with Google?" Second: a company reached out — they want their whole team on Gossip.com, but employees need to log in using their existing company account. Not create new ones.

Two different requests, same underlying ask: stop making users manage credentials with us. Let someone else handle it.

Hope looks at what building auth in-house actually means: storing passwords — which need to be hashed correctly. Password reset flows. Brute force protection. Account lockouts. Two-factor. All of it security-critical, none of it Gossip.com's actual product. And all of that work, just to compete with "it already works with my Google account."

The cleaner path: don't own identity — delegate it. The user proves who they are to Google. Google hands back a token saying "I vouch for this person." Gossip.com trusts that token and moves on. No password stored. No credential touched. That's OAuth2 — a framework for letting a trusted third party handle identity on your behalf.

OIDC — OpenID Connect — standardizes what's inside that token. So whether the user comes in through Google, GitHub, or any other provider, your system reads the same structure. One integration pattern, many providers.

For the company that reached out — same thing. Their internal identity provider, Okta or Azure AD, becomes the trusted third party. Employees log in once with their company account and get in. That's SSO — Single Sign-On. Hope didn't build it. He just plugged into what already existed.

Beat 5.2d · Docker

And then a different kind of pain. A new engineer joins the team. Setting up their local environment takes two days, three Stack Overflow tabs, and at least one "but it works on my machine." They deploy to staging — different OS, different library versions, different everything. The service crashes. Works locally, breaks in staging. Works in staging, breaks in production. Ten services, ten stacks — the Node 18 vs Node 16 situation nobody remembers why happened. Every difference between environments is a potential failure, and with ten services, the combinations are endless.

The root problem is that the service and the environment it runs in are separate things. The code is written assuming certain things exist — a specific runtime, specific libraries, specific system dependencies. If the environment doesn't match exactly, behavior changes.

What if the service carried its environment with it? Instead of shipping just the code and hoping the server has everything it needs, you package the code, the runtime, the libraries, the dependencies — everything — into one self-contained unit. That unit runs identically everywhere: your laptop, the staging server, production. Same environment, guaranteed. That's a container. Docker is what makes building and running them practical. You define what the service needs once. It runs the same way everywhere, every time.

Act 6 · 2017 · Distributed Systems

Gossip.com is now a real business. They launch premium subscriptions — no ads, exclusive gossip channels, priority feed. Users are paying. The first week goes great. Then support gets a ticket. "I was charged, but I don't have premium." Then another one. Then five more. Same pattern: payment went through. Subscription never activated.

Hope digs in. The subscription flow goes through four services. Order service creates the order. Payment service charges the card. Subscription service activates access. Email service sends the confirmation. Four separate services, four separate databases, running in sequence.

Beat 6.1 · No Shared Transaction

In a monolith, you'd wrap all of this in a single database transaction. Either everything commits, or nothing does. If something fails midway, it rolls back. Clean, atomic.

But these four services don't share a database. There is no transaction that spans all of them. Each service does its own local write and moves on. If the payment succeeds but the subscription service crashes on the next step — the payment is committed. The subscription is not. The user is charged. They don't have access. And there's no automatic rollback. Just four separate records in four separate databases, with nothing coordinating them.

This is not a bug. This is the fundamental problem of distributed transactions. And it's one of the hardest problems in distributed systems.

Beat 6.2a · Saga Pattern

The first instinct is: what if we make the services share a database again? That defeats the entire point. The whole reason we split them was isolation.

So a different approach. Instead of trying to create one giant atomic transaction across services, we accept that each step is its own local transaction — and we plan for failure at every step. When payment fails, we run a compensating action: cancel the order, mark it as failed. When the subscription service crashes, we retry. If it keeps failing, we issue a refund. Each step has a forward path and a backward path. This is the Saga pattern. Not one transaction — a choreographed sequence of local transactions, each paired with a compensation if anything goes wrong.

Beat 6.2b · Outbox + Idempotency

The Saga is in place. Payments flow, subscriptions activate, compensations fire when things fail. It holds up. For a week. Then a new ticket: "I paid but I waited ten minutes before I got access." Hope checks. The payment record is in the database. The event that was supposed to trigger the Subscription service — gone. Never published. Kafka was briefly unreachable at exactly the wrong moment, and nobody noticed because there was no error — the payment still succeeded.

After payment succeeds, the Order service does two things: writes the payment record to its database, then publishes an event to Kafka — "payment completed for order 991." The Subscription service consumes that event and activates access.

Here's the problem. Those two operations — writing to the database and publishing to Kafka — are not the same transaction. The database and Kafka are two completely separate systems. There is no atomicity between them. So if the database write succeeds but Kafka is temporarily unreachable, the event is never published. The Subscription service never receives it. The user never gets access. And no record anywhere that the event was supposed to be sent.

So the question is: how do we guarantee that the event always gets published, even when Kafka is down?

We already established that the database is our single source of truth. If something is in the database, it exists. If it's not, it doesn't. So instead of publishing the event directly to Kafka — which might fail — we write the event to the database first, in the same transaction as the payment record. Either both are saved, or neither is. That atomicity we already have.

Then a separate relay process reads those pending events from the database and publishes them to Kafka. If Kafka is down, the relay retries until it succeeds. Once published, it marks the event as done. That's the Outbox pattern. Write the event to the database first. Publish it separately. Never lose an event.

This delivery guarantee has a name: at-least-once delivery. The event will be published at least once — the relay will keep retrying until Kafka confirms it.

But "at least once" means sometimes more than once. The relay publishes the event, Kafka receives it, but before Kafka's acknowledgement makes it back — the relay crashes. It restarts, sees the event is still marked pending, and publishes it again. Now the Subscription service receives the same "payment completed for order 991" event twice. It activates the subscription twice. Maybe it charges the user twice.

So every consumer that processes these events needs to be designed to handle duplicates safely. If you receive the same event twice, the second time should produce the same result as the first — not a second action. This property is called idempotency. Before activating a subscription, the Subscription service checks: is this order already activated? If yes, skip it. Same result, no side effect. The duplicate is harmless.

At-least-once delivery is easy to guarantee. Exactly-once is extremely hard. So the practical solution is: guarantee at-least-once, and make your consumers idempotent.

Beat 6.3 · Circuit Breaker + Rate Limiting

The system now has dozens of services. They call each other constantly. And in distributed systems, there's a failure mode nobody fully anticipates: slow services.

A service that fails fast is easy to handle. You get an error, you move on. But a service that responds slowly is much more dangerous. The Feed service calls the Recommendation service. It doesn't respond. After ten seconds, it times out. While it was waiting, that request held a thread. Fifty users hit the feed at the same time — fifty threads all stuck, waiting on one slow service. No threads left for anything else. The Feed service starts timing out on everything, even requests that have nothing to do with Recommendations. Other services that call the Feed service start backing up. The whole system slows to a halt because of one slow service.

This is called a cascading failure. One service's problem becomes everyone's problem.

The solution is a circuit breaker — named after the electrical concept. You wrap calls to a service with a circuit breaker. When the failure rate crosses a threshold, say fifty percent of calls failing or timing out, the circuit opens. Instead of continuing to make calls and waiting, you fail fast: immediately return an error or a fallback, without even trying. After a timeout, you try one test request. If it succeeds, you close the circuit and resume. If it fails again, you stay open. Fail fast. Don't wait for timeouts that will never come. Protect the rest of the system from one sick neighbor.

And when you do retry — because sometimes retrying is the right call — you can't just fire again immediately. The service is already struggling. Hammering it at full speed makes recovery harder. So you back off: wait a bit before the first retry, wait longer before the second, longer still before the third. Each failure doubles the wait. That's exponential backoff.

But if you have hundreds of service instances all backing off on the same schedule, they all wake up at the same moment and hit the struggling service together. The thundering herd. So you add a small random offset — jitter — to each wait. Now they spread out. The recovering service gets a steady trickle instead of another synchronized stampede.

And at the gateway level, rate limiting. Not every threat comes from inside the system. Sometimes it's a single client making too many requests — a misbehaving script, an accidental retry loop. Rate limiting says: you get X requests per second. Beyond that, you get a 429. Try again later. It protects every downstream service from being overwhelmed by a single caller no matter how determined they are.

Outro · 2004 → 2017

And that's the system. 2004 to 2017, one gossip platform, grown into something none of us would have drawn on a whiteboard at the start.

Let's zoom out for a second.

2004: a PHP app, one server, five dollars a month. It worked. That was the right solution for that scale.

2007: traffic spiked. We scaled vertically until we hit the ceiling, then horizontally. And we discovered that distributing the load meant thinking carefully about where the state lives. Stateful became stateless.

2009: the database became the bottleneck. We learned to cache — compute once, remember the answer — and to index — give the database a map instead of making it read everything. And we pushed static content to the edge, as close to users as possible.

2011: we broke the synchronous chain. The user shouldn't wait while the server sends emails to strangers. Write a job, return immediately, process in the background.

2014: the monolith became a liability. We decomposed it — not because microservices are fashionable, but because independent teams needed to move independently. And immediately we hit the distributed systems problem: services can't share a database, but they have to coordinate. We chose availability over perfect consistency, and that choice shaped how everything communicates.

2017: we learned that distributed transactions don't exist. Not really. We learned to plan for failure at every step, to compensate instead of roll back, to never lose an event, and to protect a healthy system from a sick neighbor.

None of this was planned. None of it was drawn on a whiteboard in 2004. Every line on this architecture diagram was earned — because something broke, something was slow, something cost too much, or something was just too painful to live with anymore.

That's the thing I want you to take away today. When you're in a design meeting and someone says "we should use Kafka here" — ask why. What is the pain we're solving? Is the problem at a stage where this solution is earned? Or are we borrowing complexity from a future we haven't reached yet?

Every technology was someone's answer to a real problem. If you understand the problem, you can judge the answer. And if you're the one solving the problem, you can find the right answer for your context — not just the fashionable one.

That's it from me. Thank you.
